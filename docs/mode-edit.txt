SPIRITS EDIT MODE and COLOR EDIT MODE (SLPS-25559) - static reverse-engineering specification
==========================================================================================

Scope: mode-menu items 4 and 5. Everything below was read statically from
work/ss6/extracted/SLPS_255.59; no Probe run was used. Each statement is tagged
OBSERVED (read from instructions/data at the cited address), INFERRED (interpretation)
or UNKNOWN. Addresses are hexadecimal. "pad" is the per-seat record returned by
0x118128(seat): +0 held, +4 pressed edges, +8 pressed | directional auto-repeat
(0x117fd8: bits 0x10,0x20,0x40,0x80 from table 0x5dd840; first repeat after 20 updates,
then every 2).

0. Identification of the two scenes (settles the open question in the shared brief)
-----------------------------------------------------------------------------------
OBSERVED
  0x13ad40  SPIRITS EDIT scene entry. Calls 0x13acd8, which prints
            "customThreadGauge:STACK_SIZE=%X" (0x5e1c60) and creates task 0x13ada0. That task
            builds a list from the string table 0x4ca250 = "祭スピリッツ１".."祭スピリッツ８".
  0x13b160  COLOR EDIT scene entry. Calls 0x13f710 then 0x13b100, which prints
            "customThreadColor:STACK_SIZE=%X" (0x5e1c88) and creates task 0x13b1c8. That task
            uses 0x4ca228 (5 x "　　ボタンカラー　"), 0x4ca240 ("色をコピー","色をペースト") and
            0x5e1cb0 "デフォルトカラーに戻しますか？".
  So item 4 = SPIRITS EDIT (0x13ad40), item 5 = COLOR EDIT (0x13b160); the brief's inferred
  naming is correct. Both run with mode word 0xf (opened by seat 0) or 0x10 (seat 1) and
  0x4c38a8 = 0.
  Controlling seat: both tasks call 0x178f90() every update; for mode 0x10 it returns 1
  (0x179008), for mode 0xf it returns 0 (INFERRED for the fall-through tail after
  0x17900c, not disassembled past that point). Only that seat's pad is read.

1. Shared UI components (used by both scenes; also used by other menu scenes)
-----------------------------------------------------------------------------
1.1 Slide animator (0x34 bytes)                                              OBSERVED
  +0 curX, +4 curY, +8 remaining, +0xc duration, +0x10/+0x14 startX/Y, +0x18/+0x1c targetX/Y,
  +0x20 state (1 = retracted/"out", 0 = extended/"in"), +0x24/+0x28 outX/outY,
  +0x2c/+0x30 inX/inY.
  0x17f428(s, outX, outY, inX, inY, frames)  configure; cur = out; +0x20 = 1.
  0x17f308(s)                                = 0x17f428(s,0,0,0,0,1).
  0x17f468(s)  start moving to (inX,inY) unless target already equals it: 0x17f3c0 sets
               start = cur, target, remaining = duration = frames, +0x20 = 0 (and remaining = 0
               when cur already equals the target).
  0x17f4b0(s)  same toward (outX,outY); then +0x20 = 1.
  0x17f330(s)  per update: if remaining > 0 { r = --remaining;
                 cur = (start*r + target*(duration-r)) / duration (signed integer division,
                 X and Y separately); if r > 0 return 2 }  return (+0x20 == 0) ? 1 : 0.
               i.e. 2 = moving, 1 = settled "in", 0 = settled "out".
  0x17f400(s)  remaining < 1.
  0x17f528(event, cursor, visibleRows, scroll, rowCount) and 0x17f560(cursor, visibleRows,
  scroll, rowCount): scroll-window helpers. 0x17f560: v = min(scroll, cursor);
  if (v + visible > rows) v = rows - visible; if (cursor >= v + visible) v = cursor-visible+1;
  if (v < 0) v = 0. 0x17f528: event 3 -> scroll+visible, event 2 -> scroll-visible, otherwise
  scroll; clamped to [0, rows-visible] (negative -> 0).

1.2 List cursor (0x1c bytes; embedded at widget+0x50)                         OBSERVED
  +0 flags, +4 disabled-row bitmap pointer, +8 min, +0xc max (exclusive), +0x10 step,
  +0x14 cursor, +0x18 page size.
  Flag bits: 0x1 use repeat bits 0x10 (-step) / 0x20 (+step); 0x2 use repeat bits 0x40 (-step)
  / 0x80 (+step) (tested first; bit 0x1 only applies when bit 0x2 produced no movement);
  0x4 wrap; 0x8 invert direction; 0x10 confirm disabled; 0x20 cancel disabled; 0x80 no move
  sound; 0x100/0x200 suppress confirm/reject sound (mask 0x300); 0x100/0x400 suppress cancel
  sound (mask 0x500); 0x800 bitmap valid; 0x20000 START (0x8) does not confirm; 0x40000
  movement disabled; 0x1000/0x2000/0x8000/0x10000 are layout/ownership flags of the owner.
  0x20dff8 init: cursor 0, flags 5, range [0,1), step 1, page 0.
  0x20e028(l,min,max,step,page) (max bumped by 1 when min == max; swapped when max < min;
  page reset to 0 when page >= max), 0x20e0a0(l,bitIndex,on) set/clear flag bit,
  0x20e0d0(l,cursor) clamped/wrapped assignment, 0x20e480(l,bitmap) attach bitmap,
  0x20e4e0(l,row) DISABLE row, 0x20e528(l,row) ENABLE row, 0x20e498(l,row) test disabled.
  0x20e128(l, seat) -> event, in this order:
    pad = 0x118128(seat); p = pad.pressed;
    confirm = (p & 8) && !(flags & 0x20000) || (p & 0x202);   cancel = !confirm && (p & 0x404)
    if confirm: if (flags & 0x10) or row disabled: sound(-1,0x24) unless flags&0x300; return 6
                else sound(-1,0) unless flags&0x300; return 4
    if cancel:  if (flags & 0x20): as the rejected case above (return 6)
                else sound(-1,0x24) unless flags&0x500; return 5
    d = 0; r = pad.repeat (+8)
    if flags&2: d = (r&0x40) ? -step : (r&0x80) ? +step : 0
    if flags&1 and d == 0: d = (r&0x10) ? -step : (r&0x20) ? +step : 0
    if flags&8: d = -d;  if flags&0x40000: d = 0
    n = cursor + d; if n >= max: n = (flags&4) ? min : max-1; else if n < min:
        n = (flags&4) ? max-1 : min;   cursor = n
    if cursor changed: sound(-1,0x20) unless flags&0x80; return 1
    if page < 0 return 0
    if page > 0 and r&0x100000: cursor = max(0, cursor - page*step); ev = 2 (move sound)
    else if page > 0 and r&0x400000: cursor = min(max-1, cursor + page*step); ev = 3
    else if r&0x200000: cursor = 0; ev = 1      else if r&0x800000: cursor = max-1; ev = 1
    return cursor changed ? ev : 0
  Sound request is 0x1e7b70(-1, id): 0x20 move, 0 confirm, 0x24 cancel and rejected.
  Event codes: 0 none, 1 moved, 2 page back, 3 page forward, 4 confirm, 5 cancel, 6 rejected.
  Pad bit meaning: 0x10/0x20 up/down and 0x40/0x80 left/right (OBSERVED usage; same as
  src/character_select.cpp); 0x8 START; 0x80000 SELECT (INFERRED from the hint strings
  "SL..." shown for exactly the states where 0x80000 is tested); 0x202 = the two confirm
  buttons, 0x404 = the two cancel buttons (hint string "BP選択 BOBT決定 BXBS戻る");
  0x100000/0x400000/0x200000/0x800000 = shoulder buttons (which is L1/R1/L2/R2: UNKNOWN).

  Character list builder 0x20eae0(m, visible, firstRow, includeEx, includeKuroko, useUnlockTbl):
    sets list flag 0x10000; clears id table 0x1373830 (s16[0x37]) to -1; walks the order table

    != 0 : byte[0x43d06e + id] == 0. When includeEx != 0 and byte 0x43d0ec != 0 the four ids at
    0x59cd51 (72,74,73,75) are appended. Row label = 0x4d4bb0[id] for id < 0x32, otherwise
    fixed strings 0x664810/0x664820/0x664838/0x664850 (default 0x664800). Sets list flag 0x2000;
    0x20ee20(m) then returns the character id of the cursor row (0x1373830[cursor]).

2. SPIRITS EDIT
---------------
2.1 Entry, task, exit                                                         OBSERVED
  0x13ad40: 0x13acd8(); tail-call 0x1e7b40.
  0x13acd8: printf(0x5e1c60, 0x6000); memset(0x124a1c0, 0, 0x18000);
            0x1126f0(priority 0x32, handler 0x13ada0, stack 0x124a1c0, stackSize 0x6000, 0x20,
            tag 0x1451).
  Destructor 0x13ad60: for tag in 0x1451..0x14b4: 0x11e3a0(tag); 0x112a70(tag).
  Exit: only one path. State -1 waits for the slot menu slide to finish, then
  0x10f158() (memory-card auto-save; it returns immediately when word 0x5735c8 == 0),
  0x1252f0(1, 0, 0x13ad60, 0x127940). 0x127940 is the title/mode-menu scene entry (creates
  task 0x127a88, priority 0x14, tag 0xbbe). The mode word is not changed by this scene.

2.4 Task 0x13ada0 - objects on the task stack                                  OBSERVED
  frame (sp+0x20): 0x1822a0; 0x182318(frame, 1).
  slot menu M (sp+0x190): 0x20e570; slide (-0x130,0x50) -> (0x10,0x50), 16 frames; list flag
      0x10000; if byte 0x43d0ed != 0: 0x20e738(M, 0x4ca250, 8) (8 rows, 8 visible) else
      0x20e5d8(M,6,6) + rows 0..5 from 0x4ca250.
  editor E (sp+0xa00): 0x20d6f8(E, frame+0x60); then 0x20db50(E) (retracted, inactive).
  summary slide S (sp+0xea0): (0x2c2,0x70) -> (0xe2,0x70), 16 frames, started retracted.
  cur = -1, next = 7.

  State machine (cur at $s5, next at $s0):

       +--------------------+ confirm (4)  +----------------------+
  ---> | 7 slot list        |------------->| 8 editor             |
       | menu + summary in  |<-------------| (categories/options) |
       +--------------------+  editor      +----------------------+
              | cancel (5)     returns 5
              v
       +--------------------+ slide done: 0x10f158(); 0x1252f0(1,0,0x13ad60,0x127940); next=-2
       | -1 closing         |
       +--------------------+

  Per update, in this order:
    seat = 0x178f90(); 0x118128(seat) (result unused); 0x17c210(); 0x1825b8(frame);
    0x17f330(S); ev0 = 0x20ee70(M, 0x178f90()); ev1 = 0x20d818(E, 0x178f90());
    if next != cur:                                     (entry actions)
        7:  0x182648(frame); 0x17f468(M.slide); M.visible = 1; 0x17f468(S); M.active = 1;
            0x20db50(E); 0x1827c0(frame, 0x21, 1)
        8:  if cur < 8: 0x20d7a0(E, M.cursor);          (load the slot)
            0x20db00(E); 0x17f4b0(M.slide); M.active = 0; 0x17f4b0(S)
        -1: 0x17f4b0(M.slide); M.active = 0; 0x17f4b0(S); 0x1826b0(frame)

    else:                                               (state update)
        7:  ev0 == 4 -> next = 8;  ev0 == 5 -> next = -1
        8:  ev1 == 5 -> next = 7   (ev1 == 4 is ignored here)
        -1: if 0x17f400(M.slide): 0x10f158(); next = -2;

  immediately (2.5); cancel only leaves the current list.

3.2 Palette storage                                                            OBSERVED
  pal_all.bin is loaded at 0x408a40 (0x115208, size 0x41000). Index: key = character*5 +
  colourNumber; bank b (0..31) of 16 u16 entries at 0x408a40 + ((key*32 + b)*16)*2.
  Editable table "edit_pal_tbl" = save block + 4 = 0x5735cc, size 0x6180 bytes
  (52 characters x 0x1e0; the code iterates characters 0..50 only):
      entry(character, colour 0..4, storedBank 0..2, i 0..15) =
          u16 at 0x5735cc + ((character*5 + colour)*0x30 + storedBank*16 + i)*2
  stored bank 0 = pal_all bank 0, stored bank 1 = pal_all bank 1, stored bank 2 = pal_all
  bank aux(character), where aux = byte table 0x4ca9a8[character] (0x13be78; 0xff means "use
  bank 2"): non-0xff values: 1:20 2:22 4:20 11:3 16:26 19:21 24:20 33:23 34:25 42:20 45:20.
  Runtime copies: 0x3ec740 (player 1) and 0x3f28c0 (player 2), same layout. 0x115498 (boot,
  from 0x10f024) fills the save table and both runtime copies with the pal_all defaults and
  resets the palette cache; 0x115238(player) refills one runtime copy with defaults. The
  VS memory-card loader (state table 0x573548, 0x1b67b0..0x1b68xx) copies 0x6180 bytes from
  the loaded card image + 4 (0xdf1044) into 0x3ec740 or 0x3f28c0 depending on the port
  being read, and 0x1b6460 copies 0x3ec740 -> 0x3f28c0 when word 0x132cc18 == 1 (INFERRED:
  both players share one card). Which path fills 0x3ec740 for ARCADE/PRACTICE/SURVIVAL:
  UNKNOWN (no other writer of 0x3ec740 exists besides 0x115238/0x115498/0x1b6xxx).
  Colour format: u16, bit 15 set on every value written by the editor; three 5-bit fields
  at bits 0-4, 5-9 and 10-14. The editor converts with
      word = 0xff000000 | f(10-14) << 19 | f(5-9) << 11 | f(0-4) << 3     (0x13c9f8)
      u16  = 0x8000 | (word >> 9 & 0x7c00) | (word >> 6 & 0x3e0) | ((word & 0xff) >> 3)  (0x13ca58)
  Only entries 1..15 of a bank are shown/edited (entry 0 is never touched).

  Palette key decoding in the cache allocator 0x115d40(key, bank) -> cache slot:
      owner = (key >> 16) & 3; k = key & 0xffff; character = k / 5
      owner == 0: source pal_all bank `bank` of key k.
      owner != 0: if bank == aux(character) (or, for character 33 only, bank == aux or
                  aux + 1) then bank = 2. If bank < 3 the source is
                    owner 1: key & 0x40000 ? 0x3ec740 : key & 0x80000 ? 0x1232c80 : 0x5735cc
                    owner 2: key & 0x40000 ? 0x3f28c0 : key & 0x80000 ? 0x1232ce0 : 0x5735cc
                  at offset (k*3 + bank)*0x20 (the 0x1232c80/0x1232ce0 buffers are indexed by
                  bank only); otherwise pal_all as for owner 0.
      The slot is looked up/allocated in a 24-entry cache (identity words 0x439a48, reference
      words 0x439aa8, busy words 0x439b08, physical slot numbers 0x5dd5c8) and uploaded by
      0x116478; the cached colours live at u16 0x43ab70[slot*16 + i].
  The editor uses keys (character*5 + colour) | 0x10000, i.e. it draws directly from the save
  table 0x5735cc. Character select uses 0x40000 | owner bits (src/character_select.cpp
  already produces palette = 0x40000 + index + (custom ? (side ? 0x20000 : 0x10000) : 0)).

3.3 How an edited colour is chosen in character select / battle               OBSERVED+INFERRED
  The five colour numbers 0..4 are the five confirm buttons of character select, in the
  order of the native table paletteButtons = {0x400, 0x200, 0x2, 0x4, 0x400000}
  (src/character_select.cpp, original 0x129db0). Holding SELECT (pad.held & 0x80000) while
  pressing one of them selects the EDITED palette of that button for that side (control bits
  shifted by 6, or by 16 together with held 0x100000); without SELECT the stock palette is
  used. The edit menu labels its five rows "ボタンカラー" with the matching button glyphs
  (0x59cd58). The battle readers of the key are the character draw path (0x115d40 callers
  0x121ecc, 0x122ae8). Network mode additionally sends the three banks through 0x115ae0
  (from 0x129fb8) into 0x1232c80 + player*0x60.

6. Interaction with battle (summary)
------------------------------------
  - Mode words 0xf/0x10 never reach battle; both scenes return to 0x127940.
  - SPIRITS EDIT output: table 0x4d7068, consumed through 0x14f4e0/0x152758 by the readers in
    section 2.7 when the fighter's system is 6, slot = cfg+0xc.
  - COLOR EDIT output: table 0x5735cc, consumed through palette keys with owner bits
    0x10000/0x20000 in 0x115d40 after being copied to the per-player runtime tables
    (section 3.2). 0x116030 is a second key-based lookup that also references 0x5735cc
    (0x116054); its body was not decoded.
  - Both tables are part of the memory-card save block 0x5735c8 (+4 and +0x633c).

7. Implementation notes
-----------------------
  - One reusable list-cursor + slide-animator + list-menu implementation covers every widget
    in both scenes; the scene logic itself is the two state machines above.
  - Events are sampled for all widgets before the state switch, and a state change consumes
    one update without processing input (entry actions only).
